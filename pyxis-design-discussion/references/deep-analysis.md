# 按问题启用的深入分析

只读当前决定需要的小节。下面的例子用于说明推理方式，不规定项目应选的算法、硬件、接口或质量目标。

## 数学模型与数据表示

**触发：** 引入压缩表示、近似模型、缓存格式、数值算法，或用一种表示替代另一种表示。

先写清需要表达的对象、允许的输入、实际运算及最终观察量。区分模型在理想算术中的性质、实现精度下的行为，以及应用真正要求的质量。

1. **检查组合。** 单步能表达，不代表经过实际组合后仍能表达。用一个最小组合反例检验；必要时决定扩展表示、限制输入，或只在边界转换。
2. **检查信息。** 表示保存了哪些信息，哪些任务需要的信息已经丢失？某个守恒量、正性或排序性质能否推出目标结果，还是只约束其中一部分？
3. **检查身份与等价。** 对象身份、数值相等和业务语义相同是否需要不同判定？不要为了共用实现而抹去这些区别。
4. **检查代价所在的单位。** 列出字节数、对象数、访问频率、在途副本和转换工作。检查共同信息能否由合适的共同所有者保存，以及这会增加什么寻址或生命周期耦合。
5. **检查退化与误差。** 挑选实际可能改变选择的边界，例如数据聚集、极端尺度、空输入、有限精度或分布变化。精确性、稳定性与性能分别取证，不扩展成无目标的穷举。

**例子：** 两个局部变换各自可用旋转和轴向缩放表示，层级组合却可能产生该表示无法保留的分量。正确问题是合成后的对象需要表达什么；若系统从不允许该组合，较小表示仍可能合适。

**例子：** 压缩透明层能保住总透过率，仍可能丢失颜色与深度的关联。先用少量异色层检查输出，再将丰富压缩表示的成本与保留更多原始层比较。数学性质成立不足以决定工程选择。

**产出与退出：** 给出适用域、关键反例、误差或质量约定，以及单位成本。必需语义不成立就改方案；用户接受的近似明确保留其局限；需要目标硬件或真实数据才能比较的部分进入验证。成本是推导、读取实际数据或小原型，不默认要求形式化证明或完整性能实验。

## 并发与资源生命周期

**触发：** 新增异步、共享可变状态、资源交付、流式消费、取消、关闭或跨执行域调度。

先检查现实调用者与消费者。消费者是否必须先知道总量，是否会再次修改结果，是否需要切换线程或等待别的系统？正在生产的数据能否独立移交，提前交付是否影响继续工作？

对发生变化的交接标明：谁生产、谁拥有、谁能修改、何时可见、谁能停止、何时无人再使用。只在这些事实确实不同的地方增加状态。

重点推演最可能破坏合约的路径：

- 生产结束但消费、借用或清理仍在进行。
- 等待者取消，但底层工作没有停止。
- 多步提交只成功了一部分，或提交结果尚不明确。
- 关闭者阻塞了完成清理所必需的执行线程。
- 队列、反馈或重试策略能处理已看到的候选，却无法让尚未到达的候选获得机会。

区分数据安全、最终有机会、无饥饿、有限时间完成和吞吐目标。实际需要哪一种由需求决定；不要由 `yield`、随机抽样或反复重试的存在直接推断进展保证。概率结论需要写明候选可达、抽样关系和结果实际被消费等前提。

**例子：** 想增加流式 API 时，先看消费者是否先求总长度再一次分配。若如此，流式接口可能引入分块、排队和所有权负担，而没有增量消费收益；若真实消费者确实需要逐块结果，再设计相应背压与交付粒度。

**产出与退出：** 得到必要的交接合约和完成条件，验证最危险的时序。没有跨执行域或生命周期变化时，不要求绘制完整状态机；没有强公平需求时，不额外引入强公平机制。成本主要是源码追踪和定向时序探针。

## 系统边界与演进

**触发：** 局部选择改变公共接口、所有权、执行流程或依赖；统一多个子系统；引入平台能力；替换已有架构。

沿真实路径核对当前机制：输入由谁产生，谁作策略决定，谁执行，谁发布可用状态，谁处理失败与回收。分别确认这些机制是已实现、只写在设计中，还是来自另一个版本或宿主。

- **界定统一的内容。** 共同后端、执行合约、数据表示、业务策略和身份域可以有不同边界。能共用机制，不代表要合并所有身份和生命周期；既有 owner 能承担责任时，不另造管理层。
- **往返检查。** 局部布局影响寻址、调度和回收；系统的交付、兼容或资源约束可能迫使局部算法改变。追踪实际受影响的边，不仅列出模块名称。
- **核实能力层级。** 底层有 API，不代表上层编译、执行和回收链已支持它。把新增合约与已有机制的接线分别列出，避免低估或夸大改造范围。
- **比较演进路径。** 在适用时比较直接替换、阶段接入、缩小首版目标和暂缓。存在旧新状态共存或持久格式时检查迁移、版本和未完成工作；不为不存在的兼容需求设计长期双轨。
- **说明复杂度收益。** 删除新抽象后会失去什么必要能力？保留旧边界会让谁承担额外转换、状态或协调？没有具体消费者的扩展点可以暂缓。

**例子：** 一个后端已有多队列提交 API，渲染图仍可能只生成单条命令流。提前着色的局部并行方案还需要依赖保留、提交切分和部分失败回收。反过来，如果资源所有权已有成熟容器，接入新资源类型通常不应自动变成重建整个所有权体系。

**产出与退出：** 得到受影响的责任和依赖、最小可行改造范围、必要迁移条件及暂缓项。能力缺口影响方案成立时先解决；纯内部组织留给实现。成本是跨模块阅读，局部可逆改动不承担全系统审计成本。

## 实验与证据选择

**触发：** 争议取决于当前实现、平台语义、数值行为或实际性能；已有结论超出其证据范围。

按具体命题选择最小充分证据，不把所有命题都送进同一种验证流程：

| 需要回答的问题 | 优先证据 | 不能顺带推出的结论 |
|---|---|---|
| 某性质能否由假设推出、表示是否足够 | 推导、最小反例；数值实验帮助发现问题 | 有限样本不证明普遍性质，精确算术不等于有限精度实现 |
| API 或平台允许什么 | 对应版本的规范与能力查询 | 允许不代表更快，单个设备不代表全部平台 |
| 当前系统实际上怎么做 | 版本明确的源码、真实调用点及必要运行观测 | 类名、设计文档或另一检出的行为不等于当前运行行为 |
| 状态交接或失败路径是否符合约定 | 可控制时序的原型与定向测试 | 普通成功测试不证明所有并发交错或端到端完成 |
| 候选是否值得采用 | 对齐目标与预算的真实负载比较 | 局部指标改善不等于整体收益，候选失败不证明整个方向无效 |

性能比较需要确认实际加载的版本、配置、负载和计量边界。只在存在相关风险时增加漂移控制、重复测量和噪声分析；不要为了完整性无限扩展实验矩阵。

改动同时影响多个机制时，区分“这个完整候选值不值得采用”和“收益由哪个机制导致”。例如并行改造可以比较原流程、拆分串行、拆分并行；不必把不可分离的改造伪装成单因素实验。

每次实验预先说明它将改变哪个决定，以及什么结果意味着继续、拒绝或暂缓。停止无效搜索时保留失败范围和混杂因素，不把有限候选的失败写成没有进一步可能。

**产出与退出：** 报告命题、证据、适用条件和剩余缺口。证据足够支持当前可逆决定就继续；关键排序仍未知则补证或保留候选。历史回放可用于解释和修订方法，不能宣称已经证明节省时间或提高设计质量。
